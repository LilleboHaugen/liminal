# Roadmap

Milestones are ordered by dependency, not by calendar. A milestone is complete only when every exit
criterion is met and verified. No dates are promised.

## Ordering rationale

1. **Guardrails before code (M0).** Quality gates (architecture, traceability, hygiene, coverage, CI)
   exist before the first engine feature, so no feature is ever built without them.
2. **Headless core before graphics (M1).** ECS, jobs, math and determinism are the base for everything,
   and they can be verified completely without a GPU.
3. **Agent tooling before graphics (M2).** The probe, CLI and MCP server are how agents verify their own
   work. Building them early means every later milestone is developed with them, the same way
   recompilation projects use the original game as an oracle.
4. **Graphics in two steps (M3 RHI, M4 renderer).** The GPU layer is proven with golden images on every
   backend before renderer features are added.
5. **First genre: voxel (M5–M6).** Voxel worlds exercise chunked data, meshing, streaming, threading,
   collision and rendering at scale, without needing skeletal animation or imported art.
6. **Shipping (M7)** before widening scope, so the full path to a native build on three operating
   systems is proven early.

## Milestone kickoff rule

M0 and M1 have detailed task files today (M1's were written by its kickoff, M1-T001). When a
milestone starts, its first task is **kickoff**: resolve the open questions due at that milestone,
and write detailed task files (`docs/tasks/`) from the work items below. A task covers a spec
section, its code and its tests; kickoffs write no spec-only task (ADR-0030 Decision 5). Specs
are written by those tasks, not by the kickoff itself. Each task SHOULD fit one sub-agent in
about 20 minutes. Plans for later milestones are refined at kickoff, when the facts are known.

Parallel tracks: after M1's `liminal_core` and `liminal_math` reach `usable`, the GPU track (M3) can run
in parallel with M1/M2 work if separate agents are available. A parallel track starts only when the
project owner records it in `docs/STATUS_NOTES.md`. Until then, the pick rule in AGENTS.md (current
milestone only) applies. The owner recorded the M3 track on 2026-11-10 (ADR-0030 Decision 11): it
starts with the M3 kickoff once both crates are `usable`, M1 tasks keep priority for slots, and
the M3 kickoff orders its tasks so that a window with a triangle and then a rotating cube on
Metal come first. No M3 work item or exit criterion is dropped.

## M0 — Guardrails

Goal: the repository enforces its own rules before any engine code exists.

Work items: see `docs/tasks/M0-T001` … `M0-T010`.

Exit criteria:
- [x] Workspace builds on macOS, Windows and Linux in CI (GitHub Actions matrix).
- [x] `cargo xtask ci` runs fmt, clippy (`-D warnings`), tests, docs (`-D warnings`), check-arch,
      check-docs, trace, hygiene, status-check, coverage, and `cargo deny`, and prints a
      machine-readable JSON summary.
- [x] Each check is shown to catch a seeded violation (fixture tests in `xtask`).
- [x] `docs/STATUS.md` is generated by `cargo xtask status`.
- [x] `xtask` itself reaches maturity `usable` per `docs/specs/xtask.md`.

## M1 — Headless core

Goal: a deterministic, parallel, headless simulation core with benchmarks against established engines.

Tasks: kickoff M1-T001; review follow-ups M1-T002 … M1-T010; work items M1-T011 … M1-T052; exit
review M1-T053 (`docs/tasks/README.md`).

Work items:
- Specs + implementation to `usable`: `liminal_core`, `liminal_math`, `liminal_memory`,
  `liminal_telemetry`, `liminal_reflect`(+derive), `liminal_jobs`, `liminal_ecs`, `liminal_app`.
- `liminal_testkit` (headless subset): app harness, `step(n)`, state-hash assertions, replay of
  recorded inputs.
- Benchmark harness decision (OQ-004, resolved by ADR-0023) and first baselines in `ci/perf/`.
- Competitive benchmarks: ECS vs `bevy_ecs` and `hecs`; math vs `glam`; jobs vs `rayon`
  (comparison crates are dev-dependencies of benchmark crates only; ADR-0023).
- Example `headless_boids`: 100k agents simulated deterministically.

Exit criteria:
- [ ] All M1 crates at maturity `usable` (MUST requirements traced, coverage floors met).
- [ ] `headless_boids` gives an identical state hash over 10,000 steps across 10 runs with the same
      seed, with the scheduler running multithreaded.
- [ ] ECS, math and jobs competitive benchmark results are recorded (parity is not required yet).
- [ ] Miri passes on the test suites of every M1 crate with `unsafe = "allow"` (`liminal_math`,
      `liminal_memory`, `liminal_telemetry`, `liminal_jobs`, `liminal_ecs`), excluding tests Miri cannot
      run, each listed with a reason. Loom tests pass for lock-free primitives in `liminal_jobs`,
      `liminal_telemetry` and `liminal_ecs`.

## M2 — Agent interface v0

Goal: an agent can drive and inspect a running Liminal app without a human.

Work items:
- Resolve OQ-002 (serialization) and OQ-003 (text format). `liminal_serial`, JSON Schema generation.
- `liminal_probe`: JSON-RPC 2.0 over stdio and localhost TCP; the M2 methods listed in ADR-0019.
- `liminal_cli`: `run --headless`, `step`, `query`, `get`, `set`, `hash`, `replay`, `schema`,
  `validate`, `doctor`.
- `liminal_mcp`: MCP server exposing the probe methods as tools (own minimal implementation over
  stdio, ADR at kickoff).
- `liminal_engine` facade v0 and `prelude`.
- Agent guide `docs/guides/driving-a-liminal-app.md`.

Exit criteria:
- [ ] Scripted end-to-end test: launch `headless_boids` via the CLI, pause, step 120 frames, query
      entities, change a component, check that the state hash changes, replay, and check that the hash
      is reproduced.
- [ ] The same flow works through the MCP server from an MCP client (test uses a scripted client).
- [ ] Every probe method has a JSON Schema, and error responses carry stable error codes.

## M3 — Platform and GPU foundation

Goal: Liminal's own RHI renders correctly on Metal and Vulkan, and an agent can capture frames.

Work items:
- Resolve OQ-001 (shader language and toolchain) with a spike: prototype ≥2 candidates and compare
  them. ADR.
- `liminal_platform` (window, events, windowed runner), `liminal_input` (actions, record/replay).
- `liminal_gpu`: instance/device selection, swapchain, buffers, textures, samplers, bindless
  descriptor model, graphics and compute pipelines, command recording, synchronization, offscreen
  targets, readback, GPU timestamps. Backends: Vulkan 1.3, Metal.
- `liminal_shader` v0. `capture.screenshot` in the probe.
- Examples: `triangle`, `textured_cube`, `compute_particles`.
- CI: Vulkan golden tests on Linux using lavapipe (software). Check whether macOS and Windows hosted
  runners can run GPU tests and record the result in an ADR.

Exit criteria:
- [ ] All three examples run on macOS (Metal), Windows (Vulkan) and Linux (Vulkan). Verified by a
      human or agent on real hardware for each OS, and recorded in the journal.
- [ ] Golden-image tests for the examples pass in CI on lavapipe and locally on Metal (Metal goldens
      are stored per backend if output differs within tolerance rules, see TESTING.md).
- [ ] Vulkan validation layers report zero errors in the test suite. The Metal API validation layer
      reports zero errors.

## M4 — Stylized renderer v1

Goal: a stylized 3D scene renderer with a verified feature set and measured performance.

Work items: render graph; cameras; mesh and material system; `liminal_assets`, `liminal_scene`,
`liminal_cook` (glTF and PNG importers, ADRs); `liminal_text` (MSDF); lighting (directional, point,
spot); cel/toon ramps; flat shading; cascaded shadow maps; outlines; fog; SSAO-lite; bloom; tonemapping
and color grading; frustum culling; GPU instancing; debug draw; on-screen debug text.

Exit criteria:
- [ ] One golden test per feature, on Vulkan (CI) and Metal (local).
- [ ] Benchmark scene "forest": 50,000 instanced meshes with shadows. Frame-time budget set from the
      measured baseline and recorded in the `liminal_render` spec.
- [ ] `liminal_render` at `usable`.

## M5 — Voxel world v1

Goal: a large, editable, streamed voxel world.

Work items: `liminal_voxel` (palette-compressed chunks, naive mesher as oracle, binary greedy mesher,
ambient occlusion, sky and block light by flood fill, chunk streaming on jobs, edit API);
`liminal_voxel_render` (packed vertex format, chunk frustum and occlusion culling, upload budget per
frame); `liminal_procgen` (noise, fBm, domain warp, biome blending).

Exit criteria:
- [ ] Greedy mesher is differentially tested against the naive mesher: identical covered face sets on
      100k random chunks.
- [ ] Single block edit → updated mesh visible in ≤ 1 frame (60 Hz) on the reference machine.
- [ ] Render distance and meshing throughput budgets set and met on the reference machine. A Steam
      Deck measurement is recorded if hardware is available.

## M6 — Gameplay systems and first demo game

Goal: an original, playable voxel sandbox demo built only through the public API.

Work items: `liminal_physics` (voxel collision, character controller, raycasts, simple rigid bodies);
`liminal_audio` (mixer, spatial audio, device output; cpal ADR); `liminal_ui` (HUD, menus);
day/night cycle; `games/voxel_sandbox`.

Exit criteria:
- [ ] Demo: walk, jump, break and place blocks, day/night cycle, sound effects, HUD. Deterministic
      replay test of a 5-minute recorded session reproduces the state hash.
- [ ] Demo uses only the `liminal` facade, enforced by check-arch. M6 kickoff must add the rule:
      `games/*` crates get a registry entry kind and a facade-only dependency rule.

## M7 — Shipping

Goal: games ship as native builds for all three operating systems, and agents can start new games
from templates.

Work items: asset packaging; `liminal package` (macOS `.app` bundle, Windows `.exe` with zip, Linux
tarball against the Steam Linux Runtime, see OQ-006); save/load; settings; `liminal new` with templates;
Game Design Spec template and agent guide `docs/guides/building-a-game.md`.

Exit criteria:
- [ ] The voxel demo is packaged and run from a downloaded archive on all three operating systems.
- [ ] An agent with no prior context builds a small original game from a one-paragraph description
      using only the guides. The session is reviewed, and the friction points found become tasks.

## Later (outline only; refined at kickoff)

- **M8** Skeletal animation, blending, IK, procedural animation.
- **M9** Large stylized worlds: heightfield/SDF terrain, LOD, foliage instancing, water, sky.
- **M10** Advanced stylized rendering: GPU-driven pipeline, meshlets (where supported), GI-lite,
  volumetric fog.
- **M11** 2D module set: sprites, tilemaps, 2D physics, 2D lighting.
- **M12** Networking (deterministic lockstep and/or server-authoritative).
- **M13** Second demo game in the open-world action-adventure genre.
